# 稿件匿名互评

Flask + SQLite + 原生 JavaScript 实现的稿件匿名互评网页，无需注册。

## 启动（单条命令）

```bash
docker compose up --build
```

访问地址：**http://localhost:8000**

依赖安装随镜像构建完成，建库建表随容器启动自动完成（幂等）。SQLite 数据保存在命名卷 `review_data`（容器内 `/data/app.db`），重启后数据与链接均保留。

## 使用流程

1. 打开首页，录入 3～8 人的姓名与纯文本稿件，生成私密链接。
2. 主持人保存**主持链接**（`/h/<随机串>`），把各自的**个人链接**（`/p/<随机串>`）分发给对应的人。链接随机生成、无法找回，请妥善保存。
3. 每位参与者在自己的页面：修改自己的稿件、阅读分配到的稿件（按录入顺序循环：每人评下一人，末位评首位）、提交评审意见。
4. 主持台实时显示待交人员；当每篇当前稿件都有有效意见后，主持人点击"全部公布"一次性公布。
5. 公布后，各参与者在自己的页面看到收到的匿名意见，稿件与意见均不可再改。
6. 公布后进入澄清问答：作者可对**自己收到的那条意见**提一次问题，对应评审者答复一次；一问一答，提交后均不可修改。双方在各自参与页查看，其他参与者与主持台均看不到问答内容。

## 规则与实现要点

- **匿名性**：参与页及其接口响应不包含他人姓名字段与任何私密链接；公布前作者无法读取收到的意见；公布后的意见也不含评审人信息。
- **版本绑定**：每次改稿使稿件版本号 +1，并立即使针对该稿的已交意见失效（其他人的意见不受影响）。提交意见必须绑定所读稿件的版本号，版本不符（过期提交）会被拒绝，且不会覆盖已有的有效意见。
- **公布门槛**：仅当每篇当前版本的稿件都存在有效意见时才允许公布；公布为一次性操作。
- **并发与原子性**：所有写操作（改稿、提交、公布）都在 `BEGIN IMMEDIATE` 事务内"先检查、后变更"，任一规则不满足即整体回滚，拒绝的操作不留下部分变更；SQLite 开启 WAL 与 busy_timeout 以支持并发请求。
- **读取语义（快照一致性）**：`GET /api/p/<token>` 与 `GET /api/h/<host_token>` 的全部查询在同一个只读事务（`BEGIN`）内完成，响应中的本人稿件、分配稿件、版本、意见、问答与公布状态来自同一快照，不会拼接不同时间点的数据。快照可能完整落在公布前（`published=false`、`received=null`、问答字段为 `null`）；一旦快照中已公布，`received` 必为针对该快照当前稿件版本的有效意见，不会为 `null`。WAL 模式下只读事务不阻塞其他连接的写入，写入也不阻塞读取；无论成功、链接无效（404）还是读取异常（500），请求结束都会结束事务并释放连接。
- **澄清问答（一问一答）**：仅公布后开放。作者可对收到的有效意见提问一次（`POST /api/p/<token>/question`），对应评审者答复一次（`POST /api/p/<token>/answer`）。身份与"对应哪条意见"完全由个人链接在服务端确定，请求体只需文本；问答随参与状态在同一快照中读出：作者侧为 `received_qa`，评审者侧为 `my_review_qa`（`{question, answer}`，尚无问题为 `null`，已问未答时 `answer=null`）。问答仅向当事双方返回——其他参与者的响应与主持状态不含问答内容，也不返回对方姓名或任何私密链接。问题与答复沿用意见的非空及长度限制（不超过 100000 字）；原稿与原意见公布后仍冻结。提问/答复在 `BEGIN IMMEDIATE` 事务内先检查后写入，并有 `clarifications.review_id UNIQUE` 兜底：公布前提问或答复（409）、尚无问题时答复（409）、重复提问或重复答复（409）均整体拒绝且不改变数据，并发提交最多一次成功。提交后无修改入口。
- **前端轮询不覆盖输入**：页面定时轮询只刷新只读展示与状态；本人稿件、意见及澄清问题/答复的输入框仅在首次载入填充，问答输入框在本人提交后才锁定，轮询不会清空或覆盖正在输入的草稿。
- **旧库自动升级与持久化**：`clarifications` 表随容器启动以 `CREATE TABLE IF NOT EXISTS` 幂等创建，旧库重启后自动支持问答存储；全部数据仍在 SQLite 文件（命名卷 `review_data`，容器内 `/data/app.db`），问答随其他数据在重启后保留。

## 本地开发（不用 Docker）

```bash
pip install -r requirements.txt
python app.py
```

访问 http://localhost:8000 。数据默认写入 `./data/app.db`，可用环境变量 `DB_PATH`、`PORT` 覆盖。

## 自测

```bash
python selftest.py
```

自测使用独立临时数据库（不影响 `./data`），通过可控交错验证读取语义：在读事务暂停期间，另一连接依次完成改稿、提交新版意见与公布，继续完成的读取仍返回一致的（公布前）快照，而非 `published=true` + 旧版本 + `received=null` 的拼接结果；同时覆盖成功、无效链接（404）、读取异常（500）下的事务结束与连接释放，以及匿名隔离、改稿失效、过期拒绝、公布门槛与公布冻结等既有规则的回归。澄清问答用例覆盖：公布前提问/答复 409、无问题时答复 409、一问一答完整流程、重复提问/重复答复 409 且数据不变、非当事双方隔离（其他参与者与主持台均不可见）、文本非空与长度限制（400）、提问与答复在 20 并发线程下各仅一次成功、问答与参与状态同快照读取（暂停期间答复不产生"有问题无答复/答复在前"的拼接）、无效个人链接 404，以及旧库自动升级与重启后内容保留。

## 接口概览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/sessions` | 创建会话，返回主持链接与各人个人链接 |
| GET | `/api/h/<host_token>` | 主持台状态（含待交人员、个人链接） |
| POST | `/api/h/<host_token>/publish` | 一次性公布（不满足条件则 409 拒绝） |
| GET | `/api/p/<token>` | 参与页状态（匿名：无他人姓名/链接；公布后含收到的意见与一问一答） |
| PUT | `/api/p/<token>/manuscript` | 改稿（版本 +1，使针对它的已交意见失效） |
| POST | `/api/p/<token>/review` | 提交意见（绑定所读稿件版本，过期 409 拒绝） |
| POST | `/api/p/<token>/question` | 公布后作者对收到的意见提问（一次一问，重复 409） |
| POST | `/api/p/<token>/answer` | 评审者对该意见上的问题答复（一次一答，无问题/重复 409） |

## 澄清问答调用示例

以下 `<作者链接>` 为收到意见的参与者个人链接，`<评审者链接>` 为循环分配中评审其稿件者的个人链接；服务端依据链接自行确定对应意见，请求体只含文本。

```bash
# 公布后，作者就收到的匿名意见提一次问题
curl -X POST http://localhost:8000/api/p/<作者链接>/question \
  -H 'Content-Type: application/json' \
  -d '{"content": "请问意见中第三点具体指什么？"}'
# {"ok":true}

# 对应评审者答复一次
curl -X POST http://localhost:8000/api/p/<评审者链接>/answer \
  -H 'Content-Type: application/json' \
  -d '{"content": "第三点是指开头段落的论据不足。"}'
# {"ok":true}

# 双方各自轮询参与状态即可看到问答（同一快照）
curl http://localhost:8000/api/p/<作者链接>
# 作者侧：... "received": "<匿名意见正文>",
#         "received_qa": {"question": "请问……？", "answer": "第三点是指……"}
curl http://localhost:8000/api/p/<评审者链接>
# 评审者侧：... "my_review_qa": {"question": "请问……？", "answer": "第三点是指……"}
```

状态码：个人链接无效为 `404`；文本为空或超过 100000 字为 `400`；公布前提问或答复、尚无问题时答复、重复提问或重复答复均为 `409`，失败不改变任何数据。主持状态 `GET /api/h/<host_token>` 的方法、路径与字段保持不变，不包含问答内容。
